# Running a home server like production

*Summary: systemd units and timers, a watchdog, nightly encrypted backups to network storage, restore drills that boot the service from a restored copy, and a full snapshot of the box.*

## Units and timers

Everything ran as systemd units. I kept most of them as user units under a dedicated account with lingering enabled so they started at boot without a login. By the end, I had about 90 user units. A few system units handled backup, NFS mounts, GPU power cap, firewall, and a permission tripwire. The model ran in Docker with a `restart: unless-stopped` configuration. The box was powered off for about 77 hours straight in July, and everything came back on its own at boot. To cut power and noise I stretched 15 timers from one or two minutes to ten using drop-in files. Each drop-in reset `OnUnitActiveSec=` with an empty line before setting the new value. I had missed that this also clears `OnBootSec` and every other monotonic trigger. Eleven timers never fired after the next cold boot, including the layer that watches the watchers. Every drop-in now re-declares its base triggers. A new "sentinel tick" was killed at 120 seconds on its first run. It tried to diagnose 27 stale incidents with the model. It now has a runtime budget and may diagnose at most two incidents per run.

## The watchdog

A watchdog timer ran every two minutes. It checked the model, the door, the reviewer, and the tunnels. The watchdog could restart only a short whitelist of units. After the watchdog once restarted a healthy model, it now needs two misses at least four minutes apart before acting. An external tunnel failed for several hours even though the server retained internet access, revealing a monitoring gap. A 15-minute check pages me when the tunnel has zero ready connections but a public ping works. The alert includes the restart command. This check only reports.

## Nightly backups to the NAS

Backups used Borg 1.2 into an encrypted repository. The repository was on an NFS share attached to an Unraid NAS. A system timer ran at 03:00 with `Persistent=true`, so a missed night runs at next boot. I used `RequiresMountsFor` and a marker file check. A missing mount can never redirect the backup to local disk. Model weights, virtualenvs, and caches were excluded from backups because they are reproducible. There were 7 daily archives and 4 weekly archives. Prune and compact occurred only after a successful run. SQLite databases were staged with `.backup()`. I did not copy live files for SQLite databases. The nightly scope included the data directory, knowledge base, application state. It did not include the keys directory, tunnel credentials, systemd units, or helper scripts. The first scheduled run failed three ways: root could not open a `/tmp` lock file because of `fs.protected_regular`; the script nested two `flock` calls on one file; and root hit a root-squashed NFS export. All three failures were fixed by 03:15. A NAS reboot left a stale NFS handle on October 14. The backup failed silently for about 36 hours after that. A drop-in now remounts the share before each run. Missing sources fail the night loudly. A coverage command reads one sample per source back from the NAS.

## Restore drills that boot the service

In September, my first live drill extracted a nightly archive in 31 seconds. All 52 SQLite files passed an integrity check. The previous day's entries were present. The plan was to repeat the drill monthly and after any backup change. The second drill is called `backup rehearse`. It opens the repository read-only and does not take a lock. It checks for twice the archive's size in free scratch space. Then it extracts the archive and restores the staged database copies. It runs `PRAGMA integrity_check` on every database. It boots the actual door on the restored copy in a child process. The child process has its data directory in scratch. Its home is in scratch too. An audit hook refuses network connections. It also refuses subprocesses and access to live paths. The child process reads tasks back. It reads conversations back. It reads memory back. It writes a receipt and deletes the scratch.

## A full snapshot

I also took a full snapshot of the whole box. It went into the same Borg repository and consisted of four archives. The main archive was 1.19 TB and contained 3.92 million files. It included data, home directories, keys, units, scripts, and project trees. Unlike the nightly runs, it included the keys, units and scripts. Models and virtualenvs were left out on purpose. The rehearsal on the final nightly archive passed. 126 databases were intact. The door booted on the copy. An extraction of four real files from an October archive matched the live files by SHA-256. The passphrase is intentionally stored separately from the backup.

## What I'd do differently

I'd put the backup pool on redundant storage. The NAS pool holding the repository was two NVMe drives striped with no redundancy. Either drive failing would have taken the backups with it. I'd back up configuration and credentials encrypted every night. Keys, tunnel credentials, and units were only captured in the final snapshot. A dead drive before the final snapshot would have meant rebuilding keys, tunnel credentials, and units by hand. I'd set an alert for a missed backup from day one. A 36-hour gap was found later instead of being alerted on from day one. I'd schedule the monthly rehearsal as a timer with an alert on failure. The monthly rehearsal was previously relied upon to be remembered by the user.I'd use fewer timers. A single scheduler with a job list would have been easier to audit than 90 units.
